# Wartales Editor
# Codex Development Guide

**Purpose**

This document defines the engineering rules for implementing features in Wartales Editor.

It is intended for AI-assisted development and should be read before making changes to the project.

The project already has an established architecture.

The goal is to extend that architecture—not redesign it.

---

# Core Philosophy

Wartales Editor is infrastructure-first software.

Reusable systems are preferred over feature-specific implementations.

When implementing a feature:

1. Reuse existing infrastructure whenever practical.
2. Extend infrastructure when necessary.
3. Avoid feature-specific shortcuts.
4. Keep the architecture clean and maintainable.

Long-term maintainability always takes priority over short-term implementation speed.

---
# Required Reading

Before implementing any milestone, read the following documents in order:

1. ProjectStatus.md
2. Architecture.md
3. CodexDevelopmentGuide.md

Architecture.md defines how the editor is built.

CodexDevelopmentGuide.md defines how contributors must work within that architecture.

If implementation appears to conflict with Architecture.md, stop and explain the conflict instead of redesigning the project.


# Development Rules

These rules are mandatory.

- Keep the project compiling after every implementation step.
- Complete one milestone at a time.
- Stay focused on the active milestone.
- Never redesign completed architecture unless explicitly instructed.
- Work only from the latest project files.
- Preserve existing public APIs unless explicitly instructed otherwise.
- Preserve verified implementations.
- Never intentionally introduce duplicate implementations.
- Never produce placeholder code.
- Never produce stub implementations.
- Never leave TODO comments.
- Never remove working infrastructure in order to implement a feature.

---

# Source of Truth

The following systems are considered authoritative.

## Property State

PropertyModel.IsModified

This remains the single source of truth for modification state.

No parallel modification tracking may be introduced.

---

## Transactions

The Transaction Framework is authoritative.

Features should not bypass transaction management.

---

## Rollback

Rollback is mutation-based.

Project reconstruction is prohibited.

Rollback should occur through rollback records generated by the mutation framework.

---

## Project Mutation

ProjectMutationService owns project mutation.

Feature services should request mutations through ProjectMutationService.

Feature services should not manipulate project state directly unless the architecture explicitly requires it.

If new mutation behavior is required:

Extend ProjectMutationService.

Do not duplicate mutation logic elsewhere.

---

## Validation

Validation occurs after operations complete.

Validators should verify results.

Validators should not mutate project state.

---

# Content Creation

ContentCreationService is responsible for feature orchestration.

It should:

- Locate required project entries.
- Request mutations.
- Aggregate mutation results.
- Return ProjectMutationResult.

It should not become a second mutation framework.

---

# Operation Framework

Operations should remain lightweight.

Operations coordinate infrastructure.

They should not contain business logic already implemented elsewhere.

---

# Engineering Principles

Prefer extending an existing class over creating a parallel implementation.

Prefer reusable infrastructure over feature-specific code.

Prefer composition over duplication.

Avoid hidden behavior.

Avoid magic values.

Avoid unnecessary abstractions.

Do not create "temporary" implementations.

---

# Object Mutations

Object-valued JSON should be handled by ProjectMutationService.

Feature services should not manually synchronize PropertyModels.

Object mutation infrastructure should:

- Preserve existing JObject instances when required.
- Preserve unknown members.
- Update known members.
- Synchronize nested PropertyModels.
- Preserve rollback.
- Preserve transaction history.
- Preserve PropertyModel.IsModified semantics.

---

# Public APIs

Preserve existing public APIs unless explicitly instructed otherwise.

When extending infrastructure:

Prefer additive APIs.

Avoid breaking changes.

---

# Implementation Workflow

For each milestone:

1. Read the request carefully.
2. Identify affected files.
3. Modify only those files.
4. Keep the project compiling.
5. Prefer complete file replacements.
6. Preserve existing architecture.
7. Stop after the requested milestone.

Do not continue into future milestones.

---

# Git Workflow

Every milestone should follow this workflow.

Build

↓

Verify

↓

Commit

↓

Push

↓

Begin next milestone

Never begin a major implementation without a clean commit checkpoint.

---

# If Uncertain

If a requested implementation conflicts with the established architecture:

Do not invent a new architecture.

Do not silently redesign the project.

Instead:

- Explain the conflict.
- Identify the existing infrastructure involved.
- Recommend the smallest architectural extension required.

---

# Goal

The goal of Wartales Editor is not simply to edit game data.

The goal is to build a professional-quality editing platform with clean architecture, reusable infrastructure, safe mutation, reliable validation, and long-term maintainability.
